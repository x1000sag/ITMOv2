# Нагрузочные проверки

## Критерии приёмки (SLO)

- Ключевые эндпойнты и латентность:
  - POST /review: p50 <= N мс, p95 <= N мс, p99 <= N мс.
  - GET /health: p99 <= N мс.
- Абсолютный тайм-аут запроса сервиса (T_req): <= N с. Запросы, превышающие T_req, считаются ошибкой.
- Допустимые 5xx: доля за прогон <= N% и не более N инцидентов на сценарий.
- Допустимые 4xx:
  - Ожидаемые: 413 для diff > 20 000 символов (API-1), 422 для невалидного запроса.
  - Прочие 4xx: доля <= N%.
- REL-1: при недоступности/задержке внешнего LLM сервис возвращает контролируемый ответ за <= 10 с (тайм-аут внешнего вызова <= 10 с).
- SEC-1: секреты маскированы до отправки в LLM; отсутствие утечек секретов в исходящих обращениях и логах.
- OBS-1: отсутствует логирование содержимого diff и ответа; в логах/трейсах/метриках нет полей с полным текстом payload/response.

## Метрики и артефакты

- Источники метрик (APM/трейсинг):
  - Системные: CPU, память, GC, дисковая и сетевая активность, размер/длина очередей (если применимо), количество воркеров/потоков.
  - Трейсы: длительности по этапам (прием запроса, подготовка prompt, вызов внешнего LLM, сериализация ответа), ошибки и retries, внешние вызовы.
  - Ошибки: распределение 4xx/5xx, причины (валидация, 413, тайм-ауты), количество controlled fallback по REL-1.
- Метрики приложения:
  - Тайм-ауты и длительности вызовов внешнего LLM; число срабатываний тайм-аута <= 10 с.
  - Количество отклоненных запросов по API-1 (diff > 20k, 413).
  - Счетчик маскировок/замены секретов (SEC-1); флаг включенной маскировки.
- Метрики стенда:
  - Ресурсы узлов/подов (если k8s): CPU/Memory/Network/FS; автоскейлинг; лимиты/requests.
  - Температура/терминальные события (OOM, рестарты, throttling).
- Инструмент нагрузки: k6 (CLI или k6-operator). Допустимы эквиваленты при сохранении артефактов и метрик.
- Хранение отчетов и артефактов: artifacts/load/<дата_прогона>/
  - k6/: результаты (JSON/CSV), summary.md.
  - metrics/: выгрузки из APM/Prometheus (экспорт), скриншоты дашбордов.
  - env/: параметры прогона (env.json), конфигурация стенда (без секретов), versions.txt.
  - notes.md: наблюдения, отклонения, ссылки на инциденты.
- Дашборды: указать постоянные ссылки на APM/метрики и закрепить временные окна под каждый сценарий в notes.md.

| --- | --- | --- | --- | --- |
| Прогрев | Постепенный разгон до N RPS, длительность N мин | p95 стабилизируется <= N мс; 5xx = 0; отсутствие холодных всплесков > N мс | Разогрев кешей/соединений, прогрев JIT, стабилизация GC | k6 summary, трейсинг «до/после», графики CPU/GC |
| Базовая | Константная нагрузка N RPS, N мин | p50/p95/p99 в пределах SLO; 5xx <= N%; прочие 4xx <= N% (искл. 413/422); T_req не превышен | Производительность основного пути (POST /review), устойчивость | k6 отчет, экспорт метрик APM, окна дашбордов |
| Пик (спайк) | Резкий рост с N до N·X RPS на N мин, затем спад | p99 <= N мс во время пика; отсутствие деградации после; 5xx <= N | Эластичность, длина очередей, всплески латентности | k6 TPS/латентности, очереди/пулы, трейсы |
| Soak | Длительная нагрузка N RPS, продолжительность N мин | Отсутствие утечек памяти; стабильные p95/p99; перезапусков/OOM = 0 | Дрифт ресурсных метрик, GC, стабильность под длительной нагрузкой | k6 time-series, APM экспорт, ресурсы узлов |
| Границы (API-1) | Варьировать размер diff: {N, 10k, 20k, >20k}, N мин на пункт | Для >20k: 413; для валидных <=20k: p95 <= N; 422 для невалидных | Поведение на пороге 20k; корректность 413/422; деградация | k6 сценарии по размерам, распределение статусов |
| Отказы внешнего LLM (REL-1) | Заглушка LLM: timeout N сценариев, ошибки N%; длит. N мин | Контролируемый ответ <= 10 с; 5xx <= N%; корректная классификация ошибок | Поведение при тайм-аутах/ошибках внешнего LLM; доля fallback | k6 + логи заглушки LLM, счетчики тайм-аутов |
| Безопасность под нагрузкой (SEC-1) | Нагрузка N RPS, N мин; в payload — маркеры "секретов" | Секреты маскированы в исходящих вызовах; утечек 0; OBS-1 соблюден | Маскирование до LLM; отсутствие payload/response в логах | Отчет прокси-заглушки (санитизированный), чек-лист |

Примечание к QA-1: при базовой нагрузке выполнить выборочную проверку ответов на соответствие правилам (ссылки на строки diff/правила), фиксируя только факт соответствия/несоответствия без сохранения содержимого.

## Методология запуска

1. Подготовка стенда
   - Зафиксировать версии: commit/branch сервиса, k6 версия, конфигурации (без секретов). Записать в artifacts/load/<дата_прогона>/env/versions.txt.
   - Включить маскирование секретов (SEC-1). Проверить, что логгер выключает/маскирует payload/response (OBS-1).
   - Настроить заглушку/прокси внешнего LLM для инъекций тайм-аутов/ошибок и проверки маскирования.
   - Настроить сбор метрик (APM/Prometheus/трейсинг). Подготовить дашборды.
   - Подготовить k6 скрипты с параметрами RPS/длительность/шаблоны payload (без настоящих секретов, данные — синтетические).

2. Последовательность прогона
   - Выполнить: Прогрев -> Базовая -> Пик (спайк) -> Soak -> Границы (API-1) -> Отказы внешнего LLM (REL-1) -> Безопасность (SEC-1).
   - Между сценариями: проверить стабильность стенда, очистить очереди/кеши при необходимости; фиксировать временные окна для дашбордов.
   - Для каждого сценария: задокументировать параметры (RPS, длительность, шаблоны payload, размеры diff), сохранить k6 результаты и метрики в artifacts/load/<дата_прогона>/.

3. Фиксация версий и параметров
   - versions.txt: {service_commit, image_tag, k6_version, сценарии и их параметры, конфиг тайм-аутов (T_req, LLM <= 10 с), лимиты ресурсов}.
   - env.json: переменные окружения и флаги (без секретов). Секреты хранятся вне артефактов.
   - notes.md: отклонения, найденные узкие места, гипотезы и ссылки на задачи.

4. Критерии pass/fail
   - Сценарий = pass, если выполнены SLO для соответствующих метрик и соблюдены API-1/REL-1/SEC-1/OBS-1.
   - В случае fail: зафиксировать метрики/трейсы, минимальный воспроизводимый пример (без содержимого diff), оформить дефект.
