# ADR-0001: Доменные классы Kanban CLI

Статус: accepted

Дата: 2026-10-07

## Контекст

Проект — консольный Kanban-планировщик. Минимальные функции:
- Карточки с перемещением между колонками без позиционирования внутри колонки.
- Дедлайны на карточках (необязательные).
- Теги на карточках.
- Одна доска хранится локально в одном JSON-файле `data/board.json`.

Требуется определить минимальные доменные сущности и инварианты, чтобы обеспечить простую, предсказуемую модель и устойчивую сериализацию в JSON.

## Решение

Вводятся следующие доменные сущности и значения:

- Board
  - Поля:
    - `Name: string` — имя доски (человеко-читаемое, опционально используется в CLI).
    - `Columns: List<Column>` — список колонок. Порядок колонок значим для отображения.
  - Инварианты:
    - Имена колонок уникальны в рамках доски (сравнение без учёта регистра).

- Column
  - Поля:
    - `Name: string` — уникальное имя колонки.
    - `Cards: List<Card>` — список карточек. Порядок карт не используется для логики (перетаскивания по позициям нет).
  - Инварианты:
    - Имя не пустое.

- Card
  - Поля:
    - `Id: Guid` — уникальный идентификатор карточки, генерируется при создании.
    - `Title: string` — краткий заголовок.
    - `Description: string?` — подробности (опционально).
    - `Tags: List<string>` — список тегов (простые строковые метки).
    - `Deadline: DateOnly?` (или `DateTime?`) — дата дедлайна (опционально).
    - `CreatedAt: DateTime` — штамп времени создания (UTC).
  - Инварианты:
    - `Title` не пустой.
    - Теги уникальны в пределах карточки (сравнение без учёта регистра).
    - Дедлайн, если задан, может быть в прошлом; логический контроль сроков относится к уровню UI/команд.

Примечание: отдельная сущность `Tag` не вводится; теги — строковые значения, хранящиеся в карточке.

### Операции домена

- Создание доски: формирование пустой доски с базовыми колонками (например, `ToDo`, `InProgress`, `Done`) — конкретный набор по умолчанию задаётся уровнем CLI.
- Добавление колонки: добавляет `Column` с уникальным именем.
- Добавление карточки: создаёт `Card` и помещает в указанную колонку.
- Перемещение карточки: перевод `Card` из одной колонки в другую. Позиция внутри колонки не фиксируется; новая карточка добавляется в конец списка.
- Управление тегами: добавление/удаление строковых тегов в `Card` (без дублирования).
- Управление дедлайном: установка/очистка поля `Deadline` у `Card`.

### Хранение и сериализация

- Единственный файл: `data/board.json`.
- JSON-структура:

```
{
  "name": "My Board",
  "columns": [
    {
      "name": "ToDo",
      "cards": [
        {
          "id": "2f1a3a6c-0d0e-4a76-9a1d-7d2b22f4b1a1",
          "title": "Пример задачи",
          "description": "…",
          "tags": ["feature", "cli"],
          "deadline": "2026-10-15",
          "createdAt": "2026-10-07T10:00:00Z"
        }
      ]
    },
    { "name": "InProgress", "cards": [] },
    { "name": "Done", "cards": [] }
  ]
}
```

- Требования к записи:
  - Атомарная запись файла (возможна реализация через временный файл и замену).
  - Кодировка UTF-8; переносы строк Unix (`\n`).

### Правила валидации и ошибки

- При добавлении колонки — ошибка при конфликте имени (без учёта регистра).
- При добавлении карточки — ошибка, если колонка не найдена.
- При перемещении — ошибка, если исходная/целевые колонки или карточка не найдены.
- При добавлении тега — игнорируется/ошибка при дублировании (конкретная политика задаётся реализацией; по умолчанию игнор).

## Рассмотренные альтернативы

1. Позиционирование карточек внутри колонки — отклонено для упрощения; порядок не участвует в логике.
2. Множественные доски и файлы — отклонено, оставляем одну доску в одном файле.
3. Реестр тегов как отдельная сущность — отклонено, теги остаются строками внутри карточки.

## Последствия

- Простая модель домена упрощает CLI и сериализацию.
- Отсутствие позиционирования сокращает требования к операциям, но ограничивает гибкость отображения.
- Одна точка хранения упрощает использование, но не подходит для многопользовательского сценария и требует аккуратной записи.

## Открытые вопросы

- Точный тип поля `Deadline` в реализации (DateOnly vs DateTime) будет выбран при реализации с учётом стандартной сериализации.
- Политика по дедлайнам в прошлом — на уровне UX/команд (предупреждение или запрет).
